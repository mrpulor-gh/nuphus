# 构建与验证清单

> agent 操作纪律，不是用户文档。六个字：**最小 · 科学 · 时效**。
> 验证是时间成本，不是流程。禁止为表演严谨而重复验证、堆数量、做无意义验证。
> 未经明确指令，禁止构建 debug / release **版本产物**、跑全量测试；验证性的 `check` / `test` 不算产物流。
> Nuphus 自身仓库的 Rust 验证**一律 `--release`，且只跑受影响的单个 crate**：应用运行占着 `target/debug/`，用 debug 验证会撞 os error 32，而 release 增量比 debug 更快、占用更少（详见 §4）。注意 debug 归运行、release 归验证，两个都要用，不是二选一。

## 0. 三问门禁

发任何验证命令前逐项确认，**任一「否」即不跑**：

- [ ] 已改动文件，且改动**影响运行状态或交付结论**
- [ ] 有**结论消费方**：人 / 评审 / CI / 真机 / 联调 / 用户
- [ ] **本机能做**（做不了 → 记「受阻」+ 点名闭环人 + 停，不反复试）

反例：只删一条 `box-shadow`、只调注释排版 → 前两条为空 → 不跑。

## 1. 改动类型 → 验证动作

| 改动 | 验证动作 |
|---|---|
| 注释 / 文案 / 提示词字符串 / 排版 / 空白 / 文档 | **不跑**。写入后核对目标行即止 |
| 纯样式 CSS | 只跑相关组件单测，禁止全量 |
| 逻辑 / 分支 / 宏 / 条件编译 / 构建脚本 | fmt+lint → 编译 → 相关单测 |
| 公共契约 / 类型 / IPC 签名 | 上条 + grep 消费方调用链 |
| 依赖 / 配置 / 工具链 | 上条 + 一次最小启动 |

零行为按 diff 判定：只碰空白、注释、字符串、文档 = 零行为；触碰宏、属性、条件编译、生成代码、构建脚本 = 非零行为。

## 2. 分层：改哪层跑哪层

| 层 | 对象 | 最低验证 |
|---|---|---|
| L1 语法契约 | fmt / lint / prettier / tsc | 全局契约可全量 |
| L2 编译类型 | 编译器 / 类型检查 | 含 L1，不重跑 |
| L3 单元模块 | 直接受影响的测试 | 改逻辑 = L1 + L2 + 相关单测 |
| L4 运行态 | 集成 / 真机 / UIA / 网络 | 本机做不了即移交 |

- [ ] 没有用全量替代影响分析
- [ ] 没有重复跑上一层已经覆盖的项
- [ ] 跨 crate / 跨包 / 生成代码：按受影响交付物的**最严格**规则

## 3. 范围绑定

| 被改对象 | 规则 |
|---|---|
| 用户项目 | 先探栈再选命令，**不默认 cargo**；工具缺失记「受阻」 |
| agent 持有项目 | 只增量 `check`，禁 `build`；多处改动攒一批一次验 |
| Nuphus 仓库 | 验证一律 `--release` **最小化增量**（单 crate；debug 归运行，见 §4） |

规则互不通用。

## 4. Nuphus 仓库专则

- [ ] `cargo check --release -p <crate>` / `cargo test --release -p <crate> --lib <过滤器>`
- [ ] **分工：debug 归运行，release 归验证。** 开发时两个都要用——`cargo run` 跑应用走 debug，编译检查走 release。不要因为「省空间」去砍掉任何一侧，也不要拿 debug 去做验证。
- [ ] **验证必须 `--release`，不能用 debug**：应用跑起来后占着 `target/debug/` 的 DLL，此时 `cargo check`（debug）会撞 os error 32；release 写 `target/release/`，与运行中的应用互不干扰。
- [ ] **release 增量优于 debug 增量**：更快、占用更少。所以「反正都要编译，不如用 debug」是不成立的——选 release 在时间和空间上都是更优解，不是退让。
- [ ] **最小化增量**：只 `check` / `test` 受影响的**单个** crate，不跑全量、不多 crate 并行；多处改动攒一批一次验。目标是「用最少编译量拿到结论」，不是「多跑几个显得严谨」。
- [ ] 不新建 target；`--target-dir` 指向新路径等同新建，用完立即删除并报磁盘变化
- [ ] 验证不产产物：`cargo build --release` 出安装包属发版任务
- [ ] 改逻辑 + 改测试：攒一批一次跑；过滤器用真实测试名的**连续片段**
- [ ] 推送前只跑 CI 主干同项：fmt + tsc + prettier 全量；含 Rust 改动补受影响 crate 的 `check --release`
- [ ] 桌面 / UIA 类 → 真机或 `#[ignore]`
- [ ] **`target/debug/` 不是垃圾**：它是 `cargo run` 的运行产物，开发中本该存在。不要以「清理」为由删它，也不要在验证时图省事用它。盘紧时该报告真实占用分布（debug / release 各多少），由所有者决定处置。

## 5. 结论状态

| 状态 | 含义 | 可否交付 |
|---|---|---|
| 通过 | 预期信号已观测到 | **可** |
| 失败 | 预期信号被违反，停止交付 | 否 |
| 受阻 | 本机跑不了必需检查 | 否 |
| 跳过 | 显式不跑，须记原因与受影响结论 | 否 |
| 未闭环 | 已开始 / 后台 / 已移交，本轮无最终结果 | 否 |
| 过期 | 基线 / 工具链 / 环境 / 相关 diff 已变 | 否 |
| 已移交 | 须他人验证，须点名闭环人，否则移交无效 | 否 |
| 后台中 | 长任务仍在跑，须记输出文件与恢复点 | 否 |

- [ ] 没有把「未闭环 / 后台中 / 已移交 / 过期 / 跳过」当成通过
- [ ] 复用旧结论前，确认基线 / 工具链 / 环境 / 相关 diff 均未变
- [ ] 后台任务记全：命令、输出文件、恢复点、勿重跑标记

## 6. 记录

- [ ] 每次验证留一条：**改动 / 结论 / 消费方 / 命令 / 预期信号 / 状态**；缺字段不跑
- [ ] 无记录 = 未验证

## 7. 禁止

- [ ] 未改动先验证
- [ ] 为验证而验证 / 堆验证数量
- [ ] 给零消费方的产物做验证
- [ ] 把本机限制当任务结论
- [ ] 同一策略连续失败 2 次还凑第三次
- [ ] 验证过程写生产 / 用户目录 / 共享状态（除明确授权）
- [ ] 通过删测试、降断言、换平台、清缓存、临时环境变量、数据副本、重定义成功标准制造假绿
