# 构建与验证纪律

> 本文件是 agent 的操作纪律，不是用户文档。核心六个字：**最小、科学、时效**。
> 验证是时间成本，不是流程；禁止为表演严谨而重复验证、堆验证数量、做无意义验证。
> 未经用户明确指令，禁止构建 debug / release **版本产物**、跑全量测试——
> 验证性的 `check` / `test` 不属于「构建版本」。
> Nuphus 仓库的 Rust 验证一律 `--release` 增量（见 D 节）。

## 0. 结论状态：八态封闭集

每个**验证项**（一条验证命令及其直接产出的一组结论）有且仅有一个状态：

| 状态 | 含义 | 能否支撑交付 |
|---|---|---|
| 通过 | 预期信号已观测到 | **唯一可以** |
| 失败 | 预期信号被违反。停止交付，无证据不得改判 | 否 |
| 受阻 | 本机环境 / 工具跑不了必需检查 | 否 |
| 跳过 | 显式决定不跑。须记录原因与受影响结论，核心路径还须消费方认可 | 否 |
| 未闭环 | 已开始 / 后台 / 已移交，但本轮没有最终结果 | 否 |
| 过期 | 复用了旧结果，而基线 / 工具链 / 环境 / 相关 diff 已变，或结果本身陈旧 | 否 |
| 已移交 | 须由外部角色验证。须记录负责人与移交产物；没点名闭环人的移交无效 | 否 |
| 后台中 | 长任务仍在跑。须记录输出文件、恢复点与勿重跑标记 | 否 |

**铁律：未闭环、后台中、已移交、过期、跳过——永远不是通过。**

## 1. 默认纪律

- 只验最低充分层。影响面不清时先做轻量影响分析；禁止用全量代替分析，也禁止以「最小」为名跳过必要层。
- 只读 / 分析 / 建议 / 纯文案注释，默认不验。但建议、配置片段、命令、示例代码一旦被采纳进交付物，按采纳后的 diff 重新判定。
- 每次验证要有命令、预期信号、失败处置。失败默认停止交付；归因环境必须有证据。

## 2. 准入门禁（五条全满足才验）

1. 已做出改动；
2. 改动影响运行状态或交付结论；
3. 有明确的结论消费方：人、评审、CI、真机、联调环境或用户；
4. 验证前已完成改动路径的逻辑链路审查，口头审查也要能落到记录；
5. 本机环境做得了。

任一不满足 → 不发验证命令，记「跳过」。本机做不了 → 记「受阻」+ 点名谁验证 + 停下：不重试螺旋、不降级乱试、不把本机限制当任务结论。

> 反例（曾真实发生）：只删一条 `box-shadow` 或调整注释排版 → 第 2、3 条为空 → 不验。

## 3. 验证决策前缀（调用任何验证命令前必发）

```text
验证决策 改动=<文件+行为变化> 结论=<受影响的交付结论> 消费方=<谁读结论> 命令=<命令或NONE> 预期=<通过信号；失败信号> 范围=<A|B|C|D+跨边界> 状态=<通过|失败|受阻|跳过|未闭环|过期|已移交|后台中>
```

缺任一字段 → 不得调用验证命令。跨边界场景还须在「范围」里写清：本机验证范围、移交范围、最终闭环人。

全局卫生例外：fmt / prettier / tsc 是提交前全局契约，必须全量跑；但它们不算代码逻辑验证结论，也不豁免 Rust 编译类最小验证。

## 4. 分层模型（栈无关）

先从仓库清单 / 配置探明工具链，**禁止对用户项目默认 Rust**：

| 层 | 典型对象 | 触发时最低验证 |
|---|---|---|
| L0 影响面 | diff、调用链、依赖方向、生成代码、构建脚本 | 先确定本机范围与移交范围 |
| L1 语法 / 契约 | parse、fmt、lint、被配置为全局契约的 prettier / tsc | 全局契约可全量；普通逻辑不因此全量 |
| L2 编译 / 类型 | 编译器、类型检查 | 含 L1，不重复跑 L1 |
| L3 单元 / 模块 | 直接受影响的测试 | 改逻辑 = L1 + L2 + 相关单测 |
| L4 运行态 / 外部 | 集成、真机、UIA、网络、准生产形态 | 本机做不了即移交，不反复试 |

最小规则：改了哪层跑哪层；高层只在工具本身覆盖低层时才含低层，低层已做的不重复跑；高层通过不代表低层可跳过。全量不是影响分析的替代品。

单用例卡死：按稳定测试名精确跳过，记录跳过原因与受影响结论；涉及核心路径的跳过不得视作通过，只能移交 CI / 真机 / 用户补验。

## 5. 范围绑定

| 被改的代码库 | 适用规则 |
|---|---|
| 用户项目 | A + C |
| agent 持有项目 | B + C |
| Nuphus 仓库 | D + C |

规则互不通用。跨边界场景——monorepo、共享 CI、生成代码、跨 crate / 包依赖、用户项目引用 agent 组件或 Nuphus crate——按受影响交付物的**最严格**适用规则执行。

## A. 用户项目（任意技术栈）

1. 先探栈与工具再选命令，不默认 cargo。
2. 按第 4 节验最低充分层；不习惯性全量，不跑与改动无关的检查。
3. 工具缺失 → 记「受阻」，说明缺什么，不假装测过。
4. 本机测不了（平台 / 硬件 / 外部依赖 / 规模 / 真人判断 / 真机交互）→ 记「已移交」给 CI / 真机 / 联调 / 用户，停下；不在测不了的层反复试。
5. 产物被运行中进程锁定且停不了 → 移交 CI；不绕过，不 kill 无关进程。
6. 单用例卡死 → 按测试名精确跳过，记录原因与影响；核心路径的跳过不是通过。
7. 验证命令只作用于沙箱、临时副本、测试库；未经用户明确授权，禁止写生产、用户目录、共享状态。

## B. agent 持有项目

适用于 agent 维护的代码，其中 Rust crate：

- 只增量 `cargo check`，禁止 `build`。
- 多处改动攒一批一次验。
- 禁止新建 target；target 被占用 → 报告用户定时机。
- `--target-dir` 指向新路径等同新建 target；自建路径用完必须立即删除并报磁盘变化。
- 同一策略连续失败 2 次 → 停下重审，不凑第三次（本文件严于宪法的 3 次，按本文件执行）。
- 禁止数据副本、临时环境变量、降断言等造假绿手段。

非 Rust 的 agent 持有代码：按 A 节执行，同样遵守攒批、不产产物、失败两次即停的纪律。

## C. 执行纪律

- 预计超过 3 分钟的任务：优先后台 + 落盘 + 轮询；工具无后台模式时，一次给足超时同步等待，禁止中途杀掉重跑——长任务已完成成果会全部作废。
- shell 超时上限 1800s。超时是否杀子进程按任务分层（与执行器 `LONG_TASK_THRESHOLD_SECS` 保持一致）：
  - `timeout` ≤ 300s（普通命令）→ 杀掉止损，卡死的命令不该继续占资源；
  - `timeout` > 300s（构建 / 全量测试 / 大下载）→ **不杀**，杀掉等于让下次从零重跑。此时回报「后台中 + 勿重跑」，用输出文件与恢复点收结果；
  - 禁止一刀切：一律不杀会泄漏卡死命令，一律杀会作废长任务成果。
- 命令莫名挂起：禁用 `-PassThru -NoNewWindow`；杀进程不加管道。
- 远程等待（CI / 网络 / 第三方）：禁止循环 sleep 空转，单次查询后交还控制权并点名闭环人。本地长任务已有输出文件 / 完成信号的，可有限 sleep 后轮询。
- 同一策略连续失败 2 次 → 停下来重审，不要凑第三次。

## D. Nuphus 仓库

- **总则：Rust 验证一律 `--release` 增量**（check / test 同此）。理由：首次全量构建 release 后缓存复用，后续更快；只维护一份 release target，磁盘占用小；不被运行中的 app 锁（debug target 会被 nuphus.exe 占用，报 os error 32）。
- `cargo check --release -p <crate>` 只确认编译；禁止用验证流程做产物构建——`cargo build --release` 出安装包属发版任务，验证不产产物。
- 改逻辑 + 加 / 改测试后：攒一批，跑 `cargo test --release -p <crate> --lib <模块路径或过滤器>`；过滤器是连续子串匹配，用真实测试名的连续片段。
- 注释 / 文案 / 排版类改动：默认零行为，禁止跑构建验证。零行为按 diff 启发式判定：只碰空白、注释、字符串、文档 = 零行为；涉及宏、属性、条件编译、生成代码、构建脚本 = 非零行为。
- 运行中的 `nuphus.exe` 只锁 debug target，不影响 `--release` 验证；确需操作被锁的 debug 路径 → 报告用户定时机，禁 kill 自身。
- 桌面自动化 / UIA → 真机或 `#[ignore]`。
- CI 失败先归因三分：代码 / 环境 / 配置；归因到环境不得改代码绕过；网络类先重试。
- 推送前本地只跑 CI 主干同项：fmt + tsc + prettier 全量；若本次含 Rust 代码改动，至少补受影响 crate 的 `cargo check --release`；其余不跑。

## 6. 时效纪律

- 验证必须与改动**同轮闭环**；闭环不了就显式标记「未闭环 / 后台中 / 已移交」，不得拖成默认通过。
- 复用旧结论仅限：依赖基线、工具链、环境、相关 diff 均未变化，且记录中声明复用依据；否则记「过期」。
- 后台长任务必须写清：命令、输出文件、恢复点、预计下次读取方式、勿重跑标记——禁止让下次从零重跑。
- 远程移交必须记录负责人与移交产物；没点名闭环人的移交无效。
- 超过合理时限仍未闭环，状态只能是「未闭环」，不得当作通过。

## 7. 记录

每次验证事件留一条紧凑记录：验证决策前缀 + 结果状态 + 观测到的信号 + 盲区 / 负责人 + 时效状态。**无记录 = 未验证。**

失败处置：失败即停交付；环境归因须有证据；永不造假绿。

## 禁止

1. 未改动先验证。
2. 为验证而验证 / 堆验证数量。
3. 给零消费方的产物做验证。
4. 把本机限制当任务结论。
5. 章节误用、范围绑定错配。
6. 把未闭环 / 后台中 / 已移交 / 过期 / 跳过当作通过。
7. 验证过程写生产 / 用户 / 共享状态，除非用户明确授权。
8. 通过删测试、降断言、换平台、清缓存、临时环境变量、数据副本、重新定义成功标准等方式造假绿。
