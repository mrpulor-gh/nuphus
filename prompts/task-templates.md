## code-generation

### API/库开发

## 任务定义
用 Go 1.22 实现支持限流、熔断、重试的 HTTP 客户端封装。输入 *http.Request，输出标准响应或结构化错误。

## 上下文
- 场景：生产环境微服务间通信，单实例 2000 QPS，P99 < 500ms
- 环境：Go 1.22，仅标准库 + github.com/stretchr/testify
- 部署：作为内部 SDK 被 30+ 服务引用

## 质量基线
- 正确性：幂等请求可重试，非幂等只熔断
- 性能：连接池复用，热路径零分配
- 可维护：单文件 < 400 行，公共接口 < 5 个，单测全覆盖
- 风格：Go 官方风格，context 透传

## 架构决策
- 模式：装饰器包装 http.RoundTripper
- 状态：本地令牌桶 + 滑动窗口熔断器，零外部依赖
- 接口：Do(req *http.Request) (*http.Response, error)，错误可断言

## 反模式
禁止：panic 处理错误、init() 自动注册、全局默认实例
避免：每请求新建连接、重试无限阻塞、熔断器竞态

## 参考坐标
类似 gobreaker 的熔断语义，但内置限流和重试

## 输出要求
- client.go + circuit.go + limiter.go，完整可编译
- _test.go 覆盖正常/超时/熔断/限流/并发
- README：初始化、配置、错误处理示例

### UI 设计

## 设计目标
为 25-35 岁都市白领设计冥想 App 首页。解决"想放松但不知从何开始"的决策瘫痪，提升首日留存。

## 品牌基因
- 气质：东方极简 × 数字禅意
- 情绪：呼吸感、安全感、渐进沉浸
- 禁忌：无宗教符号、无过度装饰、无急促感

## 视觉锚点
- 色彩：雾灰白(#F5F5F0) + 苔藓绿(#7A8B7A) + 暖金点缀
- 字体：思源黑体，细字重，行高 1.8x
- 图形：圆角有机形，边缘微模糊
- 比例：极端留白，核心内容仅占 30%

## 用户体验
- 路径：开屏 → 3s 呼吸动画 → 推荐今日冥想（1 个，非列表）
- 触点：首屏仅"呼/吸"动态文字 + 底部开始按钮
- 反馈：按下如水滴入湖，涟漪扩散

## 约束
- iOS 移动端，暗黑模式适配
- 60fps 动效，包体 < 50MB

## 参考坐标
像 Headspace 的亲和但更克制，像 Apple Health 的清晰但更温暖。不要 Calm 的密集内容和商业感。

## 输出要求
高保真首页 + 暗黑变体 + 动效说明 + 设计令牌（颜色/字体/间距）

### UI 组件开发

## 任务定义
实现 React 数据表格组件：虚拟滚动、列排序、行选择、批量操作。输入列定义 + 数据数组，输出渲染结果。

## 上下文
- 场景：B 端后台，数据量 10 万行+
- 要求：首屏 < 100ms，滚动 60fps，内存不泄露
- 环境：React 18 + TS，可用 react-window
- 部署：内部组件库 @nuphus/ui，被 20+ 页面引用

## 质量基线
- 正确性：排序稳定、选择跨页保持、键盘可访问
- 性能：仅渲染可视区，滚动不触发全量重排
- 可维护：Props < 15 个，逻辑拆分为 hooks，单测全覆盖
- 风格：遵循 ESLint + Prettier 规范

## 架构决策
- 模式：渲染与数据层分离，虚拟滚动二分查找定位
- 状态：行选择用 Set<ID>，排序父组件控制或内部缓存
- 接口：`<DataTable columns={ColumnDef<T>[]} data={T[]} rowKey="id" />`

## 反模式
禁止：render 中复杂计算、index 做 key、直接操作 DOM
避免：全量渲染、排序改原数组、搜索无防抖

## 参考坐标
类似 Ant Design Table 的功能覆盖，但更轻量、无样式入侵

## 输出要求
- DataTable.tsx + useVirtualScroll.ts + useSelection.ts
- 测试覆盖：渲染/排序/选择/虚拟边界/空状态
- Storybook：基础/大数据量/自定义列/批量操作

### 代码审查

## 任务定义
审查 PR 变更集，输入 diff/patch，输出结构化审查报告。

## 上下文
- 目的：阻止有隐患代码合并
- 范围：仅审查变更文件及受影响上下文
- 标准：团队规范 + 安全基线 + 性能红线

## 质量要求
- 每条评论绑定文件:行号 + 问题类型 + 严重程度
- 区分：阻塞（必改）/ 建议（可选）/ 疑问（待澄清）
- 复杂逻辑提供改进方案，不只说"不好"

## 审查维度
正确性：边界、并发、资源泄露、错误传播
性能：复杂度、N+1、内存分配、热路径
可维护：命名、函数长度、圈复杂度、重复
安全：注入、权限绕过、敏感信息泄露、依赖漏洞
测试：覆盖率、边界用例、mock 合理性

## 反模式
禁止：凭风格偏好否决、审查非变更代码、人身攻击措辞
避免：只提问题不给方案、过度工程化建议

## 输出要求
- 摘要（通过/需修改/阻塞统计）
- 逐文件评论（文件 → 行号 → 严重程度 → 问题 → 建议）
- 高风险项详细说明（影响面 + 修复 + 验证）

### 单元测试编写

## 任务定义
为 Rust service 模块编写单元测试，输入函数签名 + 依赖关系，输出完整可运行的测试文件。

## 上下文
- 函数：验证 JWT → 查询用户 → 检查权限 → 返回 User 或错误
- 依赖：外部 HTTP（JWT 验证）、数据库、Redis 缓存
- 现状：无测试，需从零建立

## 质量要求
- 覆盖：正常路径、边界输入、错误分支、并发场景
- Mock：外部依赖全 mock，测试不依赖真实服务
- 可读：测试名描述行为（`should_return_user_when_token_valid`），Given-When-Then 结构

## 反模式
禁止：测试间共享状态、依赖执行顺序、mock 过于宽松
避免：只测 happy path、sleep 处理异步、不清理数据

## 输出要求
- service_test.rs 完整可运行
- 覆盖报告（行覆盖 + 分支覆盖）
- Mock 配置说明
- 边界用例清单（输入 → 预期 → 验证点）

### API 设计

## 任务定义
为文件存储系统设计 RESTful API v2，输入业务需求 + v1 现有接口，输出 OpenAPI 3.0 规范 + 设计文档。

## 上下文
- 功能：上传/下载/分享/版本管理/回收站，支持断点续传
- 约束：向后兼容 v1，分页统一，错误码统一

## 质量要求
- RESTful：资源命名、HTTP 方法语义、状态码正确
- 一致性：请求/响应格式、分页、排序、过滤统一
- 可扩展：预留字段、版本控制
- 安全：上传限制、路径遍历防护、分享链接过期

## 反模式
禁止：动词 URL（/getFiles）、无版本控制、无分页大列表
避免：过度嵌套资源、命名不一致、忽略幂等

## 输出要求
- OpenAPI 3.0 YAML（可导入 Swagger UI）
- 设计文档（资源定义 + 端点 + 状态码 + 错误码）
- 序列图（上传/分享/版本恢复）
- breaking change 分析（v1 兼容性）

## project-analysis

### 代码库架构审计

## 分析范围
对指定模块做架构审计。输入代码库路径，输出可操作分析报告。

## 上下文
- 目的：评估拆分可行性和重构优先级

## 输出要求
- 架构层次（树状/分层）
- 核心链路 trace（入口 → 调用 → 出口）
- 依赖图（内部 + 外部，标注方向）

### 安全审计

## 任务定义
对 Web 应用做安全渗透测试。输入应用 URL + 测试账号，输出漏洞报告。

## 上下文
- 范围：认证、授权、输入验证、会话管理、敏感数据、第三方集成
- 环境：staging 环境，与生产同配，数据已脱敏
- 合规：需满足 SOC2 Type II 控制点

## 质量要求
- 每漏洞：CVSS 评分、复现步骤、影响面、修复建议、验证方式
- 区分：确认漏洞 / 潜在风险 / 合规缺口
- 优先级：致命(24h) / 高危(7d) / 中危(30d) / 低危(90d)

## 审查维度
OWASP Top 10：注入、认证失效、敏感数据泄露、XXE、访问控制、安全配置、XSS、反序列化、已知漏洞、日志监控

## 反模式
禁止：不验证就报漏洞、报告无复现步骤、过度依赖自动化扫描器
避免：忽略业务逻辑漏洞、只扫不分析

## 输出要求
- 漏洞清单（漏洞 → CVSS → 复现 → 影响 → 修复 → 优先级）
- 合规差距分析（SOC2 控制点覆盖）
- 修复验证方案（每漏洞的 re-test 步骤）
- 安全加固建议（长期策略）

## debug-diagnose

### 崩溃根因分析

## 症状
nuphus 在 Windows 处理大文件（>500MB）时随机崩溃，无日志，仅事件查看器 0xc0000005 访问冲突。

## 上下文
- 环境：Windows 10 22H2，32GB RAM，NVMe SSD
- 触发：>500MB 必现，小文件正常，不限文件类型
- 变更：最近发布引入流式读取，此前全量加载

## 质量要求
- 证据链：每条假设有日志/堆栈/复现支撑
- 最小复现：隔离到最小可重现条件
- 根因定位到具体代码行

## 修复约束
- 不能回退流式读取（关键特性）
- 修复后验证：大文件正常 + 内存 < 2GB + 小文件不受影响

## 反模式
禁止：不验证就声称修复、try-catch 掩盖不定位根因

## 输出要求
- 根因（代码行 + 因果链）
- 修复方案（具体 diff）
- 验证步骤 + 回归清单

### 性能问题诊断

## 任务定义
诊断性能瓶颈。输入慢查询/火焰图/指标，输出根因 + 优化方案。

## 上下文
- 症状：仪表盘加载 8s，3 条 SQL 各 2-3s
- 数据量：用户 500 万行，订单 2 亿行，关联无索引
- 环境：PostgreSQL 15，主从分离，ORM

## 质量要求
- 根因：每条慢查询给出 EXPLAIN ANALYZE 分析
- 方案：索引优化、查询重写、缓存、归档，按 ROI 排序
- 验证：优化前后对比（执行时间、IO、内存），具体数字

## 反模式
禁止：不加分析直接加索引、SELECT *、循环查询
避免：单条优化不看整体影响、忽略写性能下降

## 输出要求
- 慢查询分析（SQL → 执行计划 → 瓶颈 → 根因）
- 优化方案（索引 DDL + 查询重写 + 缓存 + 预估收益）
- 验证报告（benchmark + 回归测试）
- 监控建议（告警阈值）

## scripting-exec

### 构建+测试流水线

## 命令
1. cargo clean
2. cargo build --release（预计 3min）
3. cargo test --release
4. 确认 target/release/nuphus.exe 存在 > 5MB

## 上下文
- 工作目录：项目根目录
- 依赖：Rust 1.80+、cargo、Windows SDK
- 副作用：修改 target/，清除增量缓存

## 质量要求
- 前置验证：rustc --version、磁盘 > 2GB
- 可观测：每步验证 exit code，build 失败不 test
- 隔离：不修改 src/

## 反模式
禁止：不验证 exit code 就称成功
避免：build 失败后继续执行 test

## 输出要求
- 每步结果（exit code + 耗时）
- 产物确认（路径 + 大小）
- 环境状态（磁盘变化）
